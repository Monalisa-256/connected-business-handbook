# A practical 90-day plan

The calendar is an example, not a guarantee. A simple internal routine may take less time; a regulated, customer-facing workflow may require much longer.

## Days 1–15: Understand one job

- Interview the staff who currently perform it.
- Record each step and the source of every important fact.
- Identify what must remain under human control.
- Create 20–25 anonymized examples for testing.
- Select one no-code platform and one owner.

**Deliverable:** A one-page plan and test cases.

## Days 16–30: Build a supervised version

- Configure one intake role and one specialist, or one fixed workflow.
- Connect only the sources required for the trial.
- Add a task register with job IDs and statuses.
- Produce drafts, not unattended external actions.
- Review failures with the employees who know the work.

**Deliverable:** A working workflow in a test environment.

## Days 31–45: Connect a real business system carefully

- Use official connections and narrow permissions.
- Begin with read-only queries or low-risk internal tasks.
- Verify successful actions in the source system.
- Test outages, duplicate requests and bad inputs.
- Document who can disable the connection.

**Deliverable:** An auditable, connected workflow.

## Days 46–60: Add another type of input if useful

- Add voice notes if customers regularly send them.
- Add photographs if visual support cases are frequent.
- Add document extraction if manual data entry is costly.
- Test new failure patterns specific to that input.

**Deliverable:** One proven multimodal use case—not every possible modality.

## Days 61–75: Measure value

- Review correct completion rate and rework.
- Measure staff time saved and customer outcomes.
- Check total platform, model and integration costs.
- Compare performance against the old process.
- Improve knowledge sources and permission boundaries.

**Deliverable:** A decision about whether the process is worth continuing.

## Days 76–90: Expand or simplify

- If successful, add a related workflow or another department.
- If not successful, reduce complexity or stop.
- Write a maintenance schedule and staff handover guide.
- Repeat the tests after any changes to models or tools.

**Deliverable:** A stable operating process with a named owner.

## A simple review rhythm

| When | Owner checks |
|---|---|
| Every working day during pilot | Unfinished jobs, failed runs, unusual actions |
| Weekly | Sample of completed tasks, escalations, staff feedback |
| Monthly | Costs, permissions, connected accounts, policy changes |
| After every major product or workflow update | The critical test set again |

The objective at day 90 is not "full autonomy." It is a system whose completed work, costs and limits are understood.

## What should actually exist by the end of each month?

**End of month one:** A process map, named human owner, current reference documents, task register, sample cases, first instructions, and one tested draft-only workflow. The business should be able to explain every stage without opening a vendor's dashboard.

**End of month two:** At least one working connection to a real but restricted business system, an explicit approval route, error reporting, completed dry-run tests, and enough information to calculate cost per correct outcome. Add a second modality only if the first workflow is stable.

**End of month three:** A controlled live pilot with operating evidence, written incident response, monthly review schedule, and a decision to expand, simplify or stop. “Ten agents created” is not an outcome; “200 inquiries correctly routed without exposing private data” is closer to one.

### Weekly meeting questions

| Week | Question that must be settled |
|---|---|
| 1 | Which specific customer or staff pain will we fix? |
| 2 | Where does the correct information live? |
| 3 | Which steps must stay with staff? |
| 4 | What counts as successful completion? |
| 5–6 | Can the workflow handle normal and incomplete cases? |
| 7–8 | Can it handle rejected approvals and failed connections? |
| 9–10 | How does it behave with real usage and supervised review? |
| 11–12 | What is the cost, error rate, and decision about expansion? |

If any stage exposes a serious permission or accuracy problem, pause and resolve it rather than forcing the calendar. Deadlines are planning tools, not substitutes for evidence.
