# Contributing to the handbook

This is a practical reference for people who run businesses, not a vendor promotion or a collection of demonstrations. Improvements should help someone make a better real-world decision or complete a real task more safely.

## What makes a good contribution

A strong contribution begins with a concrete situation: a customer sends two conflicting photographs, a finance clerk receives a duplicate invoice, a supervisor rejects a message draft, or a connection fails during a booking. Explain what the person needs, what the system can verify, what should happen when it cannot verify something, and what evidence would show success.

New product guidance should link to current primary documentation. Write the product's actual feature name and note plan or channel restrictions. Do not make claims such as “100% accurate,” “fully autonomous” or “works with everything” without an independently reproducible test and a clear scope.

## Writing standards

- Use clear international English, short explanations and concrete examples.
- Explain unfamiliar technical terms on first use; link to the [glossary](reference/01-glossary.md).
- Prefer exact actions—“create a draft quotation” rather than “optimize the customer journey.”
- Distinguish published product capabilities, editorial recommendations and fictional examples.
- Never place passwords, API keys, private account identifiers, customer records, patient details or company secrets in examples.
- Prefer native Markdown tables and fenced Mermaid diagrams. Do not add binary art, scripts or unlicensed images; this repository is Markdown-only.
- Link to related chapters only when the link would help the reader finish the task.

## How to propose a change using the GitHub website

Open an issue that describes the confusing instruction or missing business situation. Include the exact page and paragraph when possible. For a correction to a vendor feature, cite the official documentation and the date you checked. Make a focused edit using GitHub's web editor or submit the changed Markdown files. Preview the result in GitHub, especially large diagrams and relative links. A maintainer should review substance, links and sensitive content before merging.

## Review criteria

A chapter is ready when a business owner can state the job it describes, the inputs, who controls the actions, how to tell whether it succeeded, and what happens when it fails. If it depends on a paid plan, local regulation, administrator access or custom integration, it must say so.
